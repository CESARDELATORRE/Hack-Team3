# PR Intent Verification Strategy

## Executive Summary

## Context
As a common and recommended practice, when code is generated by agents, the feature's definition is provided on assets such as spec-docs, architecture-docs, implementation-docs and other comparable documents that provide the needed context for the agent to implement the right code (especially when working following Specs-Driven Development, but also when providing any type of intent in the form of readible documents), if possible, from the start, trying to minimize the number of loops and discussions between the developer and the agent when generating that code. If the context is too small and ambigous, the changes of obtaining code that is implementign a different thing to what you really wanted will be high. On the contrary, if the context and definition of the feature (at domain logic level, architecture level and technical implementation level) is detailed enough, the generated code will be closer to the original goals.


However, in almost 100% of the cases when the complexity of the feature is not super-simple, then, the implemention code generated by the agent usually doesn't cover 100% of the original intent or specs/docs originally provided and even further, at the same time, the code might have gone further in the implementation compared to the original intent. 
Basically, in different areas of the implementation, the code can be behind or beyond the intent.

There are two main problems to be solved here:
1. Identify those areas where the code is behind or beyond the intent.
2. Efficiently balance both areas (code or docs) by advancing/improving each side until the implementation is fully correalted to the intent docs. But being efficient here is critical, we want to do this process which usually will require several loops, in the shortest time possible, not just "work time" but end to end time for the whole process, so lags/latency in this end to end process is important to minimize. 

The two main alternatives for executing this E2E process (with human in the loop) are:

1. PR Intent Verification at the service (ADO / GitHub.com)
In this case, we target a real created PR with the code in a PR's related branch.

2. PR Intent Verification at the local developer machine
In this case, we target the code of the branch that will be used to create a PR in the service. But the real PR in the service might or might not have been already created. We compare the generated code in a local branch at the developer's machine against the intent's documents (specs, arch docs, ADO Epics, GitHub Issues, etc.)

Challenges:

- Too many differences and too fine-grained differences in the intent-verification report: 
The granularity of the differences (behind/beyond) can be too fine-grain and hence generate too many differences in the report, especially if the original docs were providing a lot of details like if providing implementation-plan docs with code-snippets, etc. - That needs to be filtered and prioritized by identifying the important and larger differences and bubbleing it up in the priority, while minimizing the small or not important differences (i.e. a difference in a code-snippet proposed) or moving the not important differences out to an appendix.

- Multiple loops are usually needed:
PR/code intent verification and balance is usually not a single shot process. The first intent verification will generate a report that usually will identify multiple if not many differences (code behind or code beyond). So, after that initial run/loop, the developer+agent will need to start advancing/balancing the code or the docs. When it think it's done, then another intent verification should be run whicn might find additional differences. This process could have a few loops, for instance 3 minimum loops/verifications each after advancing the implementations of the code or the docs. And maybe a maximum of 5 loops if in the third loop there are still significant differences.  

- Remote loops cause negative latency/lags (longer end to end time for all the loops)
Remote loops in the service inceases highly the latency and time-lags of the E2E process, since the human in the loop needs to usually be at the end of each loop for review/approval/updates on the report.
This latency is comparable, in "phylosophy") to when working with GitHub copilot coding agent: If the work to be done by the remote coding agent is not trivial or narrow (like fixing a concrete bug) but the PR implements a full feature, the chances that the generated code went to a different implementation path not exactly as desired, is high. That causes significan loops of the developer once the PR is ready. But that approach needing many loops is not afficient/agile in the service/cloud (GitHub /ADO), compared to quickly iterating locally with GitHub copilot CLI or in VSCode. The same problem happens with the multiple loops/iterations of the intent-verification.
